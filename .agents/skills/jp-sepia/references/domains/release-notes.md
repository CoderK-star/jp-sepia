# 領域 — リリースノートと告知

Changelog、GitHub Releases、版の告知、短いローンチ投稿。`professional-pass.md` と併用。Changelog より長いものには `style-pass.md` を足す。

## 人間の基線

短く、事実、ユーザー影響が先。読者は **上げるか、何が壊れるか** を決めている。その判断に仕える。型のある構成（Keep a Changelog の Added / Changed / Fixed / Removed / Security、またはそのリポジトリの癖）は期待されており、指紋ではない。

日本語リポジトリでは敬体と常体が割れる。直近ノートに合わせる。無ければ常体、動詞先の一行。

## この領域の AI 指紋

| 指紋 | 直し |
|---|---|
| 宣伝の膨張: 「このたび発表できることを大変嬉しく思います」「強力な新機能」「シームレスな体験」「ワークフローを加速」 | 変わったことを書く。機能がニュースであり、熱意はニュースではない |
| 仕組みの無い便益: 「パフォーマンスを改善」「安定性を向上」 | 数か、変更そのもの。「コールドスタート 1.8s → 0.4s」「リトライキューの競合を修正（#412）」 |
| すべての変更を一文の物語にする | 変更ごとに一行、動詞先、形容詞なし |
| 絵文字見出しと感嘆符の連打 | 既存ノートに合わせる。既定は無し |
| 旅の導入段落と、これから先の展望の締め | 両方消す。版、日付、変更、終わり |
| 重要度と無関係に、すべての項目が同じ長さの散文 | ユーザー影響順。破壊的変更が先、一言の修正が最後 |
| 「本リリースでは〜を実現しました」 | 「実現」を事実へ戻す（style-pass §3） |

## 規則

1. **破壊的変更が先**。移行手順そのもの（コマンド、設定キー、改名したフラグ）。
2. 主張は成果物を伴う。Issue / PR 番号、コミット範囲、正確な版文字列、条件つきの実測。成果物が無い主張は書かない。
3. 謝辞は短く（「thanks @name for #398」）。感謝の段落は作らない。
4. 長さはリリースに従う。パッチは三行。厚く見せるために膨らませない。
5. ユーモアと声は、そのリポジトリの履歴にあるときだけ。無い場所へ注入しない。

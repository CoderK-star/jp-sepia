# 領域 — チケットと作業指示

Issue チケット、タスク、作業指示、自分が出す側のバグ報告（返信は `dev-replies.md`）。`professional-pass.md` と併用（短答の重み）。

## 人間の基線

命令形、最小、足りる。担当は質問せずに着手でき、完了が分かる。トラッカーのフィールドテンプレは容器であり、指紋ではない。

日本語会場のタイトルは、体言止めか常体の一行が多い。敬体の長文タイトルは機械に寄る。

## この領域の AI 指紋

| 指紋 | 直し |
|---|---|
| 依頼の前に小説並みの背景 | 文脈は、担当がまだ知らないことだけ。他はリンク |
| タイトルを地の文で言い直す説明 | 説明はタイトルが止まった所から始まる |
| 自明な手順の列挙（「1. リポジトリを開く。2. ファイルを探す……」） | 自明でない手順と、正確なコマンドだけ |
| 曖昧な完了条件: 「正しく動く」「パフォーマンスが改善」 | 検証可能な基準。回すコマンドと、完了を意味する出力（「staging の負荷試験で p95 < 200ms」） |
| 完成度のためにすべてのフィールドを散文で埋める | 空は正当な値。「N/A」が、無の段落に勝つ |
| 丸い範囲の語: 「モジュールをリファクタする」「整理する」 | 具体の境界。どのファイル／関数が入るか、何が明示的に外か |
| 「適切な対応をお願いします」 | 何をして、何が完了かを書く |

## 規則

1. **タイトルは結果** であり、活動ではない（「再デプロイでリトライキューがジョブを落とす」であり「キュー問題の調査」ではない）。
2. バグ: 正確な再現（版、コマンド、入力）、期待と実際を実出力の貼付つき、頻度。再現できなければ、試したことを書く。
3. 受け入れ条件は検証可能でなければ条件ではない。
4. 繰り返さずリンクする。先行チケット、設計ドキュメント、アラート。真実の源は一つ。
5. 優先度／見積もりは正直で裸。正当化の段落を付けない。

# jp-sepia 評価プロトコル

このディレクトリは、jp-sepia の**発火・経路選択・操作契約・事実保持・読み味**を分けて評価する。AI 検出器の回避率を合格基準にはしない。検出器はモデル、題材、更新時点に強く依存し、読み手にとっての品質を直接は測らないためである。

## 対象と構成

- `cases.json` — 7 文書種別の共通ケースと 4 操作（合計 28 試験）の定義、負例。
- `fixtures/` — 各ケースの事実表と入力原稿。固有値は評価用の架空データであり、外部の事実として扱わない。
- `validate.mjs` — マニフェストと、任意の実行結果を検査する依存なしの Node.js スクリプト。

7 種別は小説、リリースノート、PR / Issue 返信、ポストモーテム、チケット、技術記事、その他の散文である。各ケースに `write`、`review`、`refactor`、`recreate` を一度ずつ適用する。

既定の出力は成果物先行・説明最小である。`verbosityCases` で、詳細要求がない場合の前置き抑制と、詳細要求がある場合の展開を別々に確認する。

## 実行前の固定条件

評価を始める前に、次を実行記録に残す。

- 実行日、エージェント名、モデル、クライアント版、温度など変更した生成設定。
- `skills/jp-sepia/SKILL.md` のコミット SHA。まだコミット前ならファイル SHA-256。
- 追加のシステム指示、会話履歴、外部ツールの有無。

設定が異なる結果は同一の比較群に混ぜない。

## エージェントへの入力

各 `fixture` を読み、対応する `operation` を明示して実行する。評価中はスキル本文以外の humanizer、スタイル変換器、検出器を併用しない。

```text
jp-sepia の評価を行う。
対象: <fixture path>
文書種別: <document_type>
操作: <operation>

facts セクションの値を変えず、存在しない具体を加えないこと。
review は診断だけを返し、本文を書き直さないこと。
```

`write` は fixture の facts だけを材料に新規起草する。その他の操作は fixture の draft を対象にする。

## 自動検査

Node.js 20 以降で実行する。

```powershell
node .\evals\validate.mjs
```

これはケースの完全性と 28 試験の展開を確認する。候補出力を JSON にまとめた後は次を実行する。

```powershell
node .\evals\validate.mjs --results .\evals\results\codex-2026-08-29.json
```

結果ファイルの最小形は次のとおり。

```json
{
  "run": { "agent": "Codex", "model": "…", "skillRevision": "…" },
  "results": [
    {
      "testId": "release-notes/refactor",
      "route": "release-notes",
      "operation": "refactor",
      "output": "候補本文",
      "manual": { "route": "pass", "operation": "pass", "facts": "pass" }
    }
  ]
}
```

候補本文では、`requiredFacts` の文字列が残り、`forbiddenTerms` が出ていないことを機械検査する。これは必要条件にすぎない。意味が同じでも表記を変えたい場合は、先に `cases.json` の不変アンカーを更新し、変更理由を記録する。

### 配布プリフライト

公開前は次も実行する。

```powershell
node .\evals\package-preflight.mjs
```

これは公開 URL のプレースホルダ、初回コミット、`origin`、発見用ミラーの正本との差を検査する。現状は公開 URL と Git 履歴が未確定なので失敗するのが正しい。プラグインを実際に導入する試験は、このプリフライトが通ってから隔離環境で行う。

## 人手評価

出力は操作名・エージェント名・モデル名を伏せ、同一ケースの原稿と候補をランダム順で日本語編集者 2 名が採点する。各項目は 1–5 点、意見が 2 点以上割れたら第 3 評価者を入れる。

| 項目 | 合格条件 |
| --- | --- |
| 事実保持 | 重大な変更・追加・欠落が 0 件 |
| 操作契約 | `review` は改稿なし、`refactor` は最小変更、`recreate` は事実を保持、`write` は facts の範囲内 |
| 経路適合 | 指定文書種別の参照ルールを守る |
| 文体 | 敬体／常体の混在がない（意図的な引用を除く） |
| 読み味 | 原稿より改善、かつ不自然な「人間らしさ」の演技を足していない |
| 既定の簡潔さ | 詳細要求がない場合、成果物の前置き説明・方法論・自己評価がない |

初回のリリース判定は、全ケースで事実保持と操作契約が合格し、各文書種別で編集者中央値が原稿より上がることとする。品質の改善を示せないケースは、検出器スコアが下がっていても合格にしない。

## 負例（誤発火）

`negativeCases` は、英語原稿の推敲依頼、単純な日本語の事実質問、コードのデバッグ相談である。ユーザーが脱 AI・リライト・人間らしさを求めていない限り、jp-sepia を起動しないことを確認する。暗黙起動を許可する設定は、再現率だけでなくこの適合率でも評価する。

## 配布互換性の別試験

このコーパスは文章品質を測るものであり、インストーラ試験ではない。公開 URL と初回コミットが確定した後、Codex、Claude Code、Grok、Antigravity を隔離アカウントまたは VM で導入し、発見・起動・更新・アンインストールをそれぞれ記録する。Windows の `install.ps1` はユーザースコープを上書きするため、日常利用中のプロファイルで試験しない。

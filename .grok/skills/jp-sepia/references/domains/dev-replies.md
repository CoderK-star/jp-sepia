# 領域 — PR / Issue 返信とレビューコメント

プルリクエストと Issue の返信、コードレビュー、スレッドの応答。`professional-pass.md` と併用（短答の重み: 事実性、具体、型どおり）。

## 人間の基線

直接、具体、比例。メンテナは第一文で論点に答え、コードかエラーを正確に引き、不同意を平明に言い、「分からない」「直さない」を真実のときに言う。簡潔は規範であり、無礼ではない。**スレッドと、メンテナの他の返信を先に読む。そのレジスタに合わせる。** 普遍の丁寧さ標準に合わせない。サンプルが無いとき、この基線を使う。

日本語会場では「ご指摘ありがとうございます」が反射で付く。初回貢献や並外れた手間のときは残してよい。毎回の開幕はチャットボット残留である。

## この領域の AI 指紋

| 指紋 | 直し |
|---|---|
| 既定の称賛／感謝: 「素晴らしい指摘です！」「詳細な報告をありがとうございます！」 | 答えから開く。感謝は本当に要るときだけ |
| 答える前に質問／ Issue を言い直す | 消す。スレッドにすでに書いてある |
| 一文で足りる答えの壁の箇条書き | 一文。長さは賭け金に比例 |
| ヘッジした非回答: 「いくつかの要因が考えられます……」、両論併記の糊 | 踏み込む。最尤の原因、確認するチェック、または正直な「分からない」 |
| バグ報告への定型共感: 「ご不便をおかけし申し訳ございません」が本文の前に三段 | 実際に要る再現情報を聞く。会場が謝罪を要求する顧客チャネルは別 |
| 締め: 「参考になれば幸いです！」「ご質問があればお気軽に！」 | 中身で終わる |
| 手元で直せるのに、返信で約束する（「確認します」） | やってからコミットを貼る |
| レビュー全体でコメント構造が完全に揃う（どれも称賛＋問題＋提案） | 散らす。一言（「nit: 誤字」）もあれば段落もある |
| 指摘サンドイッチ（良い点 → 悪い点 → 良い点）が毎回 | 重要度を先に言い、理由を付ける |

## 規則

1. **答えが先。** 評決／答えを第一文。理由は、要る分だけ後ろ。
2. 成果物を指す。`file.py:214`、コミット SHA、エラー文 verbatim、ドキュメントのリンク。コードについての主張はコードを指す。
3. 不同意は理由つきで平明に（「これだとリトライ経路が壊れる — #388」）。謝罪の包みも、称賛サンドイッチも付けない。
4. 不確実さは安く正直に。「分からない — 2.4 で再現する？」が、ヘッジ三段に勝つ。
5. wontfix / 範囲外: そう言い、理由一つ、決めたポリシーか Issue へリンクする。報告者が解読する曖昧さへ薄めない。
6. レビューでは重大度を、そのリポジトリが既に使う言葉で明示する（blocking vs nit）。

# 領域 — 技術記事とブログ

エンジニアリングブログ、チュートリアル、アーキテクチャの記録、経験報告。いちばん厚い領域。`professional-pass.md`（記事型の重み）、`discourse-pass.md` §1–3 のアウトライン／QUD、`style-pass.md`（フィクション用スロップ表は飛ばす）。

## 人間の基線

著者が実際に当たった問題が動機。設計として不均一。面白くなった所は深く、そうでない所は一行。行き止まりが一つ、読者が不同意できる見解が一つ、条件つきの数字がある。一人称は普通。敬体か常体かは媒体（Qiita / Zenn / 社内）の直近に合わせ、混ぜない。

## この領域の AI 指紋

| 指紋 | 直し |
|---|---|
| 主題の概観で開く: 「分散システムの世界では……」／読者がすでに知る定義 | 事件、バグ、目を向けさせた数字から開く |
| 「本記事では〜を解説します」 | 切る（H, K） |
| トレンチコートのリスト記事: 地の文が実は「第一に……第二に……第三に……」 | 正直な構造（本物のリスト／表）か、議論のある本物の地の文 |
| フラクタル要約: すべての節が予告し、言い、再掲する | 一度、それが生きる層で言う |
| その場で作った概念ラベル: 「可観測性のパラドックス」「設定ドリフト症候群」 | 平明な記述か、確立した用語 |
| 対称なカバレッジ: すべての代替が一段落、どれも評決が無い | 推奨に踏み込み、考えを変える条件を書く |
| 失敗がどこにも無い: すべての手順が通り、ベンチが命題を確認する | 壊れたこと、先に試したこと、次は飛ばすことを入れる。モデルは行き止まりを系統的に落とす。読者が信じる部分である |
| 一度も走っていない汎用コード（`foo`、`my_service`） | 実際の仕事から取った、走って、試した断片。スケッチならそう明示する |
| 条件の無いベンチ | マシン、版、データサイズ、試行数。無ければ数字を刷らない |
| 両論の結び＋今後の展望 | 推奨か、自分が本当に持っている未決の問いで終わる |
| 「いかがでしたでしょうか」「参考になれば幸いです」 | 消す（K: 日本語技術記事の最頻シグナルの一つ。ウェイターではない） |
| 「こんにちは、〇〇です」が毎回の開幕 | 媒体の本人が本当にそう書いているなら残す。注入しない |
| Swallow 逆説 | 日本語特化モデルは語彙が自然で、結びが技術ブログの定型（K）。語彙は触らず、定型の器を切る |

## 規則

1. **主題より問題が先。** 第一段落: 問いを強制した具体の状況。実状況が無ければ、正直なジャンルは「X についてのメモ」であり、戦記ではない。事件を捏造しない。
2. 見解を最低一つ、自分のものとして書く。不同意の条件つき（「書き込みが秒 1k 未満なら、これを全部無視してよい」）。
3. 深さの予算は興味であり、対称ではない。驚いた節は、準備手順の 5 倍の語を取ってよい。
4. 数字は条件を伴う。主張はリンクを伴う。コードは「これは走る」か、免責を伴う。
5. QUD: 節の問いが「X とは → なぜ X が大事 → どうやる → まとめ」なら、実際に起きたことの周りへ組み直す。
6. 声: 一人称、傍白を一、二。測定された人間マーカー（立場、不均一、生きた具体）は、訓練された読者が「人が書いた」と判断する材料と同じである。
7. 自分しか書けない情報（数値、固有名、失敗）を最低一つ残す。それが無い記事は、語彙を消しても第 3 層が残る（Rapls）。

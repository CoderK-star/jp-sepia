# 実務パス — 非フィクションの共有層

リリースノート、PR / Issue 返信、障害報告、チケット、技術記事、物語でないすべての文書に適用する。根拠: slop taxonomy（Shaib et al., S）、専門家検出（Russell et al., R）、ジャンル一致（Reinhart et al., P）、Wikipedia/humanizer の記録（W）、日本語 180 本測定（K）、humanizer-jp（H）、Zaitsu & Jin（Z）。

> 実務ジャンルの目標は検出器を欺くことではない。情報が載り、立場があり、名義人の声に聞こえることである。型のある構成はここで *正しい*。スロップは型の中の埋め草である。

## 会場を先に読む

書く・直す前に、同じ会場の人間が書いた直近成果物を 2–3 見る。リポジトリの過去リリース、メンテナの最近の返信、チームの前回障害報告。測られた AI っぽさの半分はレジスタ不一致である。モデルは会場を問わず、均一に研磨された漢語の多い散文を出す（P）。目標の声を決めるのはこのスキルではなく、会場コーパスである。コーパスが無いとき、領域ファイルの基線を使う。

文体（敬体／常体）は SKILL.md のとおり、ここで固定する。混ぜない。

## チェックリスト

一度に一つ（同時パスは盲になる。この taxonomy で測定済み）。スロップは **累積**: 一発は何でもない。固まりは書き直し。

| # | 確認 | 探すもの |
|---|---|---|
| 1 | チャットボットの残留 | 「素晴らしい質問です」「ご指摘ありがとうございます！」（反射のとき）、「お役に立てれば幸いです」「ご質問があればお気軽に」「もちろんです！」「おっしゃる通りです」、「詳しく見ていきましょう」。同僚はサポート窓口のように話さない。会場が本当に使う挨拶（顧客メールの「お世話になっております」）は容器であり、残してよい |
| 2 | 密度 | 半分の長さで同じことが言えるか。どの文脈でも真である一般論（「昨今のビジネス環境において」「ここで重要なのは」）は情報ゼロ。切る。長さは賭け金に比例する |
| 3 | 関連 | すべての段落が *読者の仕事* — 知りに来たこと — に仕えるか。読者がすでに持つ背景、質問の言い直し、範囲の観光は埋め草 |
| 4 | 立場 | 判断が要る所で一つに踏み込む。必要な主観の欠如は測定されたスロップ次元（S）。評決の無いレビュー、推奨の無い比較、認めた誤りが無い障害報告。ヘッジは本当に脆い主張に一度。文ごとにしない |
| 5 | 具体 | 版、数、`file:line`、コマンド、エラー文の verbatim、名前 — あり、かつ **実在**。捏造の具体で埋めない。自信ありげな誤りは最上段の指紋（R）。無い情報は聞くか、明示 TODO |
| 6 | 書式の指紋 | 地の文で足りる所の太字ミニ見出しリスト、飾り絵文字、すべての節が同じ長さ、どこでもちょうど三項目、見出しを直後の一文が言い直す、フラクタル要約（予告 → 本論 → 各層で再掲）（W）。技術文書の正当な箇条書きはホワイトリスト |
| 7 | 結びの残留 | 「まとめ」「最後に」で言ったことを言い直す節、汎用の展望（「今後も改善を続けてまいります」）、「いかがでしたでしょうか」「参考になれば幸いです」（K: 日本語技術記事の最頻シグナルの一つ）。中身が終わった所で終わる |
| 8 | 型どおり | 同じ文枠の再利用。すべての項目が同一の言い回し。散らすか、表にする |
| 9 | リズムの同一 | 段落と文の長さが全文均一。人間の実務文は不均一。要る所は深く、要らない所は一行（H。discourse-pass §4） |
| 10 | 口調 | 文法は正しいが口に出せない漢語の列。音読して、その会場のメールに書かないなら、話し言葉の形へ |

そのあと `style-pass.md` §2–4 の語彙・構文スキャンを通す（禁止表は実務にも当てる。フィクション用スロップ表は当てない）。

密度カウントから除外: コード、インラインコード、表、コマンド／パス、用語集、参考リンク（style-pass §2）。

## 領域の重み

どの確認が支配するかは文書の形による（S で測定）:

| 文書の形 | 先に見る |
|---|---|
| 記事型（障害報告、技術記事、告知） | 関連、密度、立場／口調、一貫 |
| 短答（PR / Issue 返信、レビュー、チケット） | 事実性、具体、型どおり — 短い長さでは密度と口調の比重は下がる |

重みは注意の順と深さであり、免除ではない。埋め草に溺れた短い返信は、密度で落ちる。

長文（記事、障害報告）は `discourse-pass.md` §1–3 のアウトライン試験と QUD も走らせる。各段落の第一文がきれいな要約になり、問いの列が「説明 → 正当化 → 帰結 → 反省」なら機械型。技術記事の「結論 → 理由 → 具体例 → まとめ」も同じ位置を占める。

## 報告の型（review 操作）

```text
JP-SEPIA REVIEW — <文書種, 会場>
Loaded: <使ったファイル>
Venue corpus: <サンプリングした成果物, または "none — 領域の基線">
Failed: <#n 確認名 — 引用証拠>   （落ちた確認ごとに一行）
Passed: <番号だけ>
Verdict: <clean / 孤立ヒット / クラスタ> → <ship / refactor / recreate>
```

## ホワイトリスト — 型があること ≠ スロップ

| 旗を立てない | 理由 |
|---|---|
| Changelog のカテゴリ、Issue / PR テンプレ、RFC 節、ランブックの見出し | 共同体が期待する容器 |
| 正式な場の敬語と漢語 | レジスタ一致が、無理な口語に勝つ |
| 本当に列挙できる項目の箇条書き | 列挙事実には表とリストが正しい |
| 短い、飾らない返信 | 開発会場の人間既定は簡潔であり、指紋ではない |
| 筆者本人の確認済みの癖 | 汎用の「人間」ではなく、その声へ寄せる |
| 「お世話になっております」など会場の挨拶 | チャットボット在庫と容器を混同しない |

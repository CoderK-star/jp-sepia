# 領域 — 障害報告とポストモーテム

障害報告、障害振り返り、RCA。`professional-pass.md` と併用（記事型の重み: 関連、密度、立場）に加え、`discourse-pass.md` のアウトライン試験。

## 人間の基線

人には非難せず、仕組みには容赦しない。本物の文書は絶対時刻、正確な故障機構（クエリ、設定行、競合の窓）、正直な行き止まり（「誤った仮説に 40 分使った」）、実際に誰かが持つアクションを持つ。チームの障害テンプレは容器として正しい。指紋は中の埋め草である。

日本語の社内文書は常体が多い。対外お詫びは別文書であり、混ぜない。

## この領域の AI 指紋

| 指紋 | 直し |
|---|---|
| 行為者の霧: 「ミスが発生した」「変更がデプロイされた」で誰も何も主体を持たない | 非難しないことと、主体が無いことは違う。系と役割を名指す。「デプロイパイプラインが検証前に設定を昇格した」 |
| 汎用の教訓: 「監視とコミュニケーションを改善します」 | アクションは変更であり、所有者と期限を持つ。「キュー深度 > 10k のアラートを足す（担当: infra、期限 09-15）」 |
| テンプレのすべての節を、完成度のために同じ長さで埋める | 節は長さを稼ぐ。「うまくいったこと: 無内容の散文」→ 正直な一行か削除 |
| 自賛の副詞: 「チームは迅速に特定し……」 | 速さの判断は時刻が運ぶ。副詞に任せない |
| ヘッジした根本原因: 「複合的な要因が寄与した可能性があります」 | 信じている因果を言い、本当に不明な部分を不明と書く |
| 信頼性文化についての説教の結び | アクションで終わる |
| 丸い、出典の無い数字 | 実時間、実被害半径、実ユーザー／リクエスト数 — 実データから。完成して見せるための見積もりをしない |
| 「再発防止に向けて、適切な対策を講じてまいります」 | 「適切」を具体の変更へ戻す |

## 規則

1. **絶対時刻とタイムゾーンの時系列**。誤った曲がり角を含む。悪い仮説の 40 分がいちばん教える。モデルは失敗の中の失敗を系統的に落とす。
2. 故障機構をコード／設定の水準で。正確なクエリ、フラグ、上限、競合。書き手が知らなければ、チームへの質問であり、散文で埋める空白ではない。
3. 反実仮想は正直に。何が捕捉したか、なぜそれが無かったか。「設計どおりに動いただけです」の保身を書かない。
4. 寄与要因は因果の鎖であり、箇条書きの雲ではない。各要因は、何を可能にしたかを言う。
5. 影響は数字が先（継続時間、失敗リクエスト、影響ユーザー、分かっているなら金）、物語は後。
6. 立場確認（professional-pass #4）: 誤判断を一つも認めない障害報告は、まだ書かれていない。
